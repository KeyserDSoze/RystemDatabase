# Rystem Database performance: reproducible baselines and fair comparisons

> **Experimental, not a ranking.** Low latency is the engineering objective,
> but Rystem Database has **no validated claim** to be the fastest database,
> and no competitor latency number is valid without the **same workload,
> hardware, durability and equivalent semantics**. Start with issue
> [#12](https://github.com/KeyserDSoze/RystemDatabase/issues/12)
> and comparison work [#89](https://github.com/KeyserDSoze/RystemDatabase/issues/89).

## First measured engine: embedded Rust append-only storage (#88)

Prerequisites: Rust 1.89+, Cargo; no extra dependencies.

```sh
cargo test --locked -p rystemdb-storage --test performance_contract
cargo run --release --locked -p rystemdb-storage --example bench_storage -- \
  --records 128 --operations 256 --payload-bytes 128 --seed 42 \
  --json-output storage-benchmark.ndjson
python3 scripts/check_storage_benchmark.py --self-test
python3 scripts/check_storage_benchmark.py storage-benchmark.ndjson
```

The example creates a **fresh local temporary directory**, measures one
process, and deletes that directory when finished. Its deterministic
synthetic RDB corpus contains byte arrays, signed integers, booleans,
explicit nulls, arrays, typed references and an optional nested object:
one out of three documents contains extra fields. `--payload-bytes`
is the size of the binary **field**, not the overall document, RDB frame
or total dataset. Random access is generated by a seeded, repeatable
xorshift* sequence. Each invocation has a distinct fresh storage root.
CLI inputs are bounded to 1–8,192 records, 1–4,096 operations, and
0–8,192 binary payload bytes.

The code verifies each stored and retrieved typed value; a wrong result
**fails the run**. It samples operation API elapsed time using
`std::time::Instant` in nanoseconds. Correctness checks occur after
each timed sample and are excluded from the per-operation p50/p95/p99;
the separately reported **loop-wall throughput** does include harness
verification and timer overhead. p50/p95/p99 are **nearest-rank**
order statistics (rank ceil(n * fraction)), not interpolated percentiles
or an average of percentiles. Duration conversion is exact nanoseconds
to decimal milliseconds before display rounding. Empty samples, integer
overflow, deterministic workload generation and typed RDB roundtrips
have independent TDD unit/integration tests.

| Workload (exact NDJSON name) | What is timed | Durability / cache boundary |
| --- | --- | --- |
| `put_sync` | `DocumentStore::put` on a new ID | Single CRC RYSF frame synced before acknowledgement |
| `get_hit_typed_crc_warm` | `DocumentStore::get` on an existing ID | Already-warmed OS file cache; actual CRC + RDB decode |
| `get_miss` | `get` on an ID not in the in-memory map | In-memory index rejection, no disk read; **not comparable to a query that reaches disk** |
| `get_two_batch_members_sequential_warm` | Two separate `get` calls on different IDs in the **same BATCH3 frame** | Both verify the complete frame CRC and decode the batch independently |
| `get_two_batch_members_grouped_warm` | One `get_many([a,b])` for the exact same two keys and seeded schedule | One physical open/metadata/CRC/whole-batch decode for that frame; report **per two-key request**, not per document |
| `snapshot_capture` | Copy current historical index + tombstone ledger | In-memory O(distinct historical IDs) metadata clone |
| `update_sync` | `put` replacing an ID | CRC frame + sync, checksum and typed result checked afterward |
| `staged_batch_2_sync` | Create a staged batch, stage 2 distinct IDs and commit | **Includes staging**, one 2-key CRC batch with one sync |
| `delete_sync` | Delete one existing ID | Synced tombstone |
| `reopen_replay` | Reopen database and replay all segments | **One sample** only, not meaningful p95/p99; writer close is outside the timed sample |

Each NDJSON run records the engine, version, embedded-vs-network mode,
OS/architecture, seed, cardinality, operation count, payload bytes,
cache/durability description and nanosecond/millisecond units.
Per-workload rows record sample count, p50/p95/p99/max, total loop time
and loop-wall ops/s. The two grouped-vs-sequential workloads use the **same two keys,
physical frame, random operation schedule, typed results and CRC
validation**. Both are measured on the same engine and runner in the
same invocation, but the modes execute sequentially rather than
interleaved; cache and background runner noise may bias either number.
They do **not** measure the single-key `get` path and do not
represent PostgreSQL/SQLite/RocksDB comparisons. No winner claim can
be based on one shared-runner sample.

A final row records total benchmark elapsed time,
on-disk bytes and segment count. This is **not a persistent process
memory benchmark** and does not measure true cold filesystem cache:
reopening a file is not the same as evicting it from the OS page cache.
The benchmark performs only synchronous single-writer operations; it
does not measure queueing, multithread contention, network RTT or
database server connection pooling.

`seed=42`, `records=64`, `operations=128`,
`payload_bytes=128`, on code commit
[`1defb065`](https://github.com/KeyserDSoze/RystemDatabase/commit/1defb065ebfdf366022e115295b0f76e5b04a5f3),

[CI #45207441976](https://github.com/KeyserDSoze/RystemDatabase/actions/runs/45207441976).

details; it is not a production SLA, dedicated-host baseline or
competitor comparison.

| Warm GET + CRC + typed decode | 128 | 0.002834 | 0.003146 | 0.005255 |

Measured segment data: **70,016 bytes**, one segment. The missing-ID

### Automated CI telemetry

The Linux Rust CI job runs the **release** example with fixed small
inputs (`64/128/128/42`) and validates its NDJSON using the
dependency-free Python checker (six self-tests, including five negative schema cases).
The original Rystem report plus the exported RDB fixture and SQLite WAL/FULL report are uploaded together as a short-retention
`storage-benchmark-<commit SHA>` GitHub Actions artifact. These are
per-commit, shared-runner diagnostic results; they are NOT controlled
repeatable performance baselines. **Only correctness, schema,
nonempty samples and bounded input are CI pass/fail conditions. There is
no absolute millisecond gate** to produce spurious red CI on noisy hosts.

## Indexed metadata/stat avoidance for hot GET (#97)

Previously each live `DocumentStore::get` and
`DocumentSnapshot::get` opened the on-disk RYSF segment and called
`File::metadata()` before decoding it. In the new indexed-only read
path, the already-replayed ID index provides the segment/offset; a
dedicated private helper reuses the **same whole-frame RYSF CRC and
typed-RDB decoder** without first asking the file size. Truncated
header/body errors now surface as `Corrupt` through `read_exact`;
missing files remain I/O errors. Replay still uses the segment's
actual file length for safe recovery of incomplete final frames.
The grouped multi-key reader also skips the single stat call per
segment. The number of explicitly requested filesystem metadata
operations is therefore reduced by **one per successful single GET**
and **one per opened segment per grouped get_many call**.
No new persistent file handles, memory cache, wire or storage format.

This establishes **a code-path syscall reduction, not a measured
response-time improvement**. OS implementations, CPU costs and cache
behavior differ; existing `get_hit_typed_crc_warm` and grouped
benchmark rows automatically observe the new path. Per-commit
GitHub-hosted p50/p99 values remain subject to large I/O noise.
This change does not fix the throughput comparison parity gap:
native SQLite typed GET omits Rystem's outer RYSF CRC. Further
statistically meaningful old/new A/B on dedicated hardware remains
open in [#90](https://github.com/KeyserDSoze/RystemDatabase/issues/90).

## Five fresh-database alternating-order native benchmark repetitions (#96)

Child [#96](https://github.com/KeyserDSoze/RystemDatabase/issues/96) provides a
**Python-stdlib-only orchestrator** for the already compiled Rust
Rystem and standalone native Rust SQLite benchmark executables.
It validates the fixture and individual reports **before** computing
any results; no timings of compilation or the initial fixture export
enter either engine's five measured repetitions.

```sh
cargo build --release --locked -p rystemdb-storage --example bench_storage
cargo build --release --locked --manifest-path benchmarks/sqlite-native/Cargo.toml
python3 scripts/test_paired_benchmark.py
python3 scripts/paired_benchmark.py \
  --rystem-bin target/release/examples/bench_storage \
  --sqlite-bin benchmarks/sqlite-native/target/release/rystemdb-bench-sqlite \
  --out-dir paired-benchmark \
  --repetitions 5 --seed 42 \
  --records 32 --operations 64 --payload-bytes 64
```

The runner first creates exactly one **uncounted** Rystem fixture,
records its SHA-256 and validates its metadata. Each measured Rystem
run then creates **its own fresh RYSF database**, and each native SQLite
run creates **its own fresh WAL/FULL database**, all consuming the
same fixture seed, record count, key order and typed RDB values.
The first engine alternates between Rystem and SQLite, deterministic
from the seed: Rystem/SQLite, SQLite/Rystem, Rystem/SQLite,
SQLite/Rystem, Rystem/SQLite for five iterations and seed 42.
Other seeds reverse the starting order. A fixed sequence and a
new database root do **not** imply independent cold OS page cache.

The report validator checks every run's schema, typed RDB integrity
disclosure, sample count, seed, cardinality, payload size, engine
versions and OS/architecture. Any mismatch, malformed payload,
timeout or failed process makes the entire job fail with no successful
aggregate. All **10 raw measured reports**, the source RDB fixture
and the uncounted preflight report are retained separately. A final
`paired-benchmark/summary.ndjson` contains run order and a
**median of five per-run p50, p95 and p99 statistics**, together
with min/max across those five run statistics. The values are not
percentiles of pooled observations, confidence bounds, or guarantees
for future requests. Host/kernel, logical CPU count, SHA, engine
versions, payload, fixture hash and cache/durability/integrity
limitations are reported. There are no hard CI millisecond thresholds
and no cross-engine "winner" field.

**Limitations:** this is a shared, non-CPU-pinned GitHub host,
with non-controlled OS page cache and possible background I/O.
Five repetitions reduce order sensitivity but do not make these
results equivalent to five experiments on a reserved machine.
The two-key Rystem workload includes staging while SQLite's
two-row transaction uses a different API, and Rystem GET verifies
an additional full outer **RYSF CRC** unavailable in SQLite.
Their on-disk formats, compression/indexing and sync protocols
also differ. Neither a durable performance SLA nor an assertion
that Rystem is the "fastest database in the world" is established.
Parent #93 remains **OPEN** for dedicated-host, controlled cache,
real concurrency, 1K/100K/1M datasets, resource profiling and
integrity parity. Parents #89/#12 remain OPEN for other engines.

## Native Rust SQLite typed-RDB comparison (#94; child of #93)

The follow-up to #92 adds an **isolated** `benchmarks/sqlite-native`
Cargo project. It is **not a member of Rystem's production workspace**;
only the benchmark-only crate depends on `rusqlite` with bundled SQLite,
`serde_json` and the existing local Rystem codec/storage crates.
Neither the production Rystem `Cargo.toml` nor the storage format
acquires a SQLite dependency. The standalone dependency graph uses a
separate lockfile, and the native driver runs only in the Linux
benchmark CI step.

```sh
# First reproduce the exact #92 typed RDB fixture on the same host:
cargo run --release --locked -p rystemdb-storage --example bench_storage -- \
  --records 64 --operations 128 --payload-bytes 128 --seed 42 \
  --json-output storage-benchmark.ndjson \
  --fixture-output storage-fixture.ndjson

# Native driver uses rusqlite to open a separate real SQLite WAL/FULL DB:
cargo test --locked --manifest-path benchmarks/sqlite-native/Cargo.toml --all-targets
cargo run --release --locked --manifest-path benchmarks/sqlite-native/Cargo.toml -- \
  --fixture storage-fixture.ndjson \
  --output sqlite-rust-benchmark.ndjson
python3 scripts/check_native_sqlite_benchmark.py --self-test
python3 scripts/check_native_sqlite_benchmark.py \
  --native-report sqlite-rust-benchmark.ndjson \
  --rystem-report storage-benchmark.ndjson
```

The native driver parses and validates **the same exact Rust-exported
canonical RDB v1 bytes** for every original value, update and two-key
batch; it independently recreates the seeded key-order and typed
synthetic document with Rystem's codec. Invalid metadata, out-of-order
keys, oversized inputs and valid-but-tampered documents fail before
benchmarking. Every acknowledged SQLite INSERT/UPDATE/DELETE uses
`BEGIN IMMEDIATE` / `COMMIT` with verified `WAL` and `FULL`;
two rows in one batch use **one** SQLite transaction, rolling back both
when either write fails. Prepared SELECTs are cached. Every measured
warm-hit read includes actual `rystemdb_core::decode` and returns
the typed value plus exact original bytes, with correctness checked
outside the timed sample. Tests cover typed nested data, references,
nulls, explicit corrupt-BLOB rejection, atomic rollback, and reopen
persistence.

The independent native report labels
`driver=native_rust_rusqlite` and
`payload_semantics=rdb_v1_typed_decode_no_rysf_outer_crc`,
and captures the **actual bundled SQLite engine version**, Rust
process OS/arch, per-operation nanosecond/millisecond
p50/p95/p99, loop-wall throughput and disk/WAL/SHM footprint.
It is stored alongside existing Rystem and Python SQLite raw reports
under a single per-SHA artifact. **The measured native GET does
decode RDB, but SQLite does not have Rystem's outer CRC-protected RYSF
frame**. Production equivalence, query language and transaction
isolation are not yet established. An early shared-runner sample is
not a definitive ranking or per-request SLA.

## First real SQLite WAL/FULL exploratory baseline (#92, child of #89)

**This is deliberately not a speed ranking.** The benchmark now exports
the **exact same binary RDB v1 frames and randomized key/operation order**
used by Rystem's release-mode `bench_storage` example. A standard-library
Python `sqlite3` adapter loads those bytes as **opaque SQLite BLOBs**
and times actual embedded, disk-backed CRUD with
`PRAGMA journal_mode=WAL`, `PRAGMA synchronous=FULL`,
explicit `BEGIN IMMEDIATE` + `COMMIT` **per individual write**,
and **one transaction for each two-key batch**. The adapter verifies
that both PRAGMAs took effect, that reads and writes return **exactly**
the exported RDB bytes, and that the final data survives closing and
reopening SQLite. It reports the actual SQLite library and Python
runtime versions, not assumed versions.

```sh
python3 scripts/test_sqlite_benchmark.py
cargo run --release --locked -p rystemdb-storage --example bench_storage -- \
  --records 64 --operations 128 --payload-bytes 128 --seed 42 \
  --json-output storage-benchmark.ndjson \
  --fixture-output storage-fixture.ndjson
python3 scripts/check_storage_benchmark.py storage-benchmark.ndjson
python3 scripts/benchmark_sqlite.py \
  --fixture storage-fixture.ndjson \
  --rystem-report storage-benchmark.ndjson \
  --output sqlite-benchmark.ndjson
```

Fixture rows are **bounded**, versioned NDJSON: metadata, all initial
document ID + fully encoded RDB hex values, each exact seeded read-ID,
each update ID + full replacement RDB hex, then two keys and typed
values for each batched atomic write. An independent validator rejects
unexpected/missing fields, duplicate/out-of-order document IDs,
malformed hex/magic/types, nonmatching read/update key orders,
overlimit files, records/operations/payload sizes and incorrect
metadata across the two engines. Exporting is outside Rystem's timed
operations and does **not** alter its RYSF storage format or hot paths.
Fixture export deliberately caps inputs to 256 initial records,
512 operations and 1,024 payload bytes so the generated hex corpus
cannot silently become huge.

The SQLite workload uses a `TEXT PRIMARY KEY` table with non-null
`BLOB` payloads, cached prepared statements, one writer process
and a fresh temporary on-disk database. Its measured operations are:

| SQLite metric | Meaning and alignment limits |
| --- | --- |
| `put_sync` | Insert the **same RDB frame bytes** as Rystem, one WAL/FULL commit per key |
| `get_hit_raw_blob_warm` | Query the same prewarmed seeded existing IDs, retrieve opaque RDB BLOB (**no CRC or typed RDB decode**) |
| `get_miss` | Index miss by identical absent-key pattern |
| `update_sync` | Replace the same keyed RDB frame bytes, one WAL/FULL commit per update |
| `batch_2_sync` | Insert the same two RDB-valued keys in **one SQLite transaction** |
| `delete_sync` | Delete original keys one by one, each with WAL/FULL commit |
| `reopen_replay` | Open SQLite after close; **one sample** with validation, not a directly equivalent RYSF replay |
 
The report includes nanosecond samples and rounded millisecond
p50/p95/p99/max, wall-loop throughput, database+WAL+SHM disk bytes
while active, sqlite3 runtime version, Python version, and explicit
`payload_semantics=opaque_rdb_blob_no_typed_crc_decode`. The
**SQLite `get_hit_raw_blob_warm` is not directly comparable to
Rystem `get_hit_typed_crc_warm`**: Rystem CRC-checks its RYSF frame
and decodes typed RDB values; SQLite/Python fetches opaque bytes and
compares them for equality outside the timed sample. The runtimes
(Rust vs Python), storage layouts, journal and indexes, caching,
transaction implementation, write verification/throughput accounting
and reopen behavior also differ. The new results can identify a
performance region to investigate, **not** establish a fair
winner/speedup percentage.

GitHub's **single shared Linux CI runner** runs both engines in
sequence and uploads `storage-benchmark.ndjson`,
`storage-fixture.ndjson` and `sqlite-benchmark.ndjson`
in the existing per-commit artifact. The independent Python unittest
suite and fixture/report format tests are correctness gates; **no
millisecond limit or ungrounded superiority assertion is in CI**.
Raw numbers are subject to runner contention and cache drift. The
official SQLite documentation confirms that WAL with `synchronous=FULL`
synchronizes the WAL at every commit; see
[SQLite PRAGMA synchronous](https://sqlite.org/pragma.html) and
[SQLite WAL](https://sqlite.org/wal.html).

## Competing systems and necessary workload parity (#89)

Competitors cover different tasks, and **must not** be mixed into one
"fastest database" leaderboard.

| Scenario | Rystem path | Relevant competitors / tools | State |
| --- | --- | --- | --- |
| Embedded single-key PUT/GET/DELETE | Rust `DocumentStore` | SQLite WAL/FULL; RocksDB `db_bench` with synchronous writes | **Rystem + SQLite opaque-RDB Python baseline measured; fair native comparison pending** |
| Embedded 2-key durable atomic write | Rust BATCH3 commit | SQLite one explicit 2-row transaction; RocksDB `WriteBatch` with sync | **Rystem + SQLite WAL/FULL measured; transaction overhead differs** |
| Client/server document CRUD | Future comparable Rystem RSWP RPC load | PostgreSQL JSONB; MongoDB document protocol with equivalent networking | **not yet benchmarked together** |
| Key-value mixes / hot keys / scans | Future uniform workloads | YCSB A–F with identical distribution and record counts | **not yet benchmarked together** |
| SQL aggregations and analytical scans | Future SQL/DataFusion/Parquet path | PostgreSQL, DuckDB (their analytical benchmark suites) | **Rystem SQL path not implemented: N/A** |
| Secondary-index and reference joins | Future Rystem transactional index/relation path | PostgreSQL and other query engines | **Rystem features not implemented: N/A** |

Before quoting competitor milliseconds, collect identical input fixtures,
key order, schema semantics, decoded vs opaque value behavior,
synchronization mode and errors; run all engines on the same isolated
machine/storage. **SQLite `WAL`+`synchronous=FULL`** commits include
a WAL sync each transaction, unlike `NORMAL`; durability settings
strongly change write latency. For RocksDB set an equivalent synchronous
write contract. PostgreSQL via a socket must be compared with the
Rystem **RPC** path, not the faster embedded function call. DuckDB's
analytical workloads belong in their own category. When a feature does
not exist, display **N/A**, not a zero-millisecond result.

Recommended independent official benchmark methodologies:

- [YCSB standard workloads](https://github.com/brianfrankcooper/YCSB/blob/master/doc/coreworkloads.html)

### Next experimental protocol before any ranking

1. Pin engine versions, OS/kernel, CPU/core count and governor, RAM,
   storage device/FS/mount, concurrency, protocol and durability mode.
   Save all actual command lines, backend configs and source SHA.
2. Start with 1,000 / 100,000 / 1,000,000 documents, small and nested
   payload tiers (e.g. 128 B, 1 KiB and 16 KiB), specified sparsity and
   reference distributions; report total disk footprint separately.
3. Warm up, then measure at least **five independent fresh runs per
   workload**, plus cold and warm cache separately. Publish raw samples,
   median across runs and p99 distribution; do not cherry-pick the minimum.
4. Include read-hit/miss, acknowledged durable insert/update/delete,
   optimistic conflict/no-op, multi-key batch, sorted prefix scan,
   restart/replay, and concurrent YCSB mixes. Record each result's
   semantic support, errors and timeout behavior.
5. Profile slow operations before optimizing, then rerun the same
   corpus/hardware. Use dedicated machines for any latency regression
   budget; CI's shared hosts only check functional validity and retain
   samples for diagnosis.
